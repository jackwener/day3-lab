## 1. 背景与动因

研报是证券研究机构的核心产出物，发布前须经过严格的合规审核与内容质量检查。当前审核流程高度依赖人工，存在以下痛点：

| 痛点                                                                             | 来源                             |
| -------------------------------------------------------------------------------- | -------------------------------- |
| 人工审核效率低：单份研报审核耗时 10-45 分钟，质检员每天处理 15-20 份，工作强度大 | S-01 需求澄清会议、S-03 用户访谈 |
| 合规风险漏检：敏感信息识别依赖审核员经验，隐晦表述容易漏检                       | S-01 需求澄清会议、S-03 用户访谈 |
| 审核标准不统一：不同审核员的判定结果差异大，缺乏客观统一的审核规则               | S-01 需求澄清会议                |
| 审核记录追溯困难：纸质或零散电子记录，问题定位与统计分析耗时                     | S-01 需求澄清会议                |

## 2. 项目目标

构建 **研报审核助手**，在研报发布前自动化执行合规审核与内容检查，核心目标：

| 目标         | 量化指标                                                     |
| ------------ | ------------------------------------------------------------ |
| 提高审核效率 | 单份研报审核耗时缩短 50% 以上（从 10-45 分钟降至 5-20 分钟） |
| 降低漏检率   | P0 级合规问题漏检率趋近于零                                  |
| 统一审核标准 | 规则引擎 + AI 审核双保障，消除人为判定差异                   |
| 审核可追溯   | 所有审核记录、问题详情、修改建议全量留痕，支持统计分析       |

## 3. 范围边界

| 做（In-Scope）                                       | 不做（Out-of-Scope）                        |
| ---------------------------------------------------- | ------------------------------------------- |
| 研报文件上传与解析（支持 PDF / DOCX / DOC）          | 用户认证与权限管理（MVP 阶段不涉及）        |
| 规则审核 / AI审核 / 规则+AI联合审核三种模式          | 研报编辑功能（仅审核，不修改原文）          |
| 审核报告生成与展示（含问题定位、严重程度、修改建议） | 第三方系统集成（如 OA 审批流、邮件通知）    |
| 审核历史列表查询（分页、筛选、搜索）                 | 多租户 / 行级数据权限                       |
| 规则管理（查看规则列表、启用/禁用规则）              | 自定义规则创建（仅支持预置规则的启用/禁用） |
| 仪表盘统计（概览指标、趋势图、TOP5 问题）            | 实时推送 / WebSocket 通知                   |
| 审核报告导出（PDF 格式）                             | 研报自动采集 / 爬虫功能                     |

## 4. 利益相关方

| 角色     | 关注点                                   | 使用频率    |
| -------- | ---------------------------------------- | ----------- |
| 研究员   | 提交研报审核、查看审核报告、根据建议修改 | 每天多次    |
| 质检员   | 执行审核、查看问题详情、导出报告         | 每天持续    |
| 合规专员 | 管理审核规则、查看合规统计               | 每周多次    |
| 质检主管 | 查看仪表盘统计、审核趋势分析             | 每天 1-2 次 |
| IT 部    | 系统部署与维护                           | 按需        |

## 5. 核心假设与约束

| 类型 | 内容                                                |
| ---- | --------------------------------------------------- |
| 假设 | 研报文件格式为 PDF / DOCX / DOC，单文件大小 ≤ 50MB  |
| 假设 | AI 审核依赖外部大模型 API，网络可达时启用           |
| 假设 | 审核规则由合规专员预先定义，系统内置初始规则集      |
| 约束 | MVP 阶段使用 SQLite 作为数据库，不支持高并发场景    |
| 约束 | 前端采用多页面架构（非 SPA），基于原生 JavaScript   |
| 约束 | AI 审核服务不可用时，系统 MUST 降级为纯规则审核模式 |

## 7. 风险初步评估

| 风险               | 影响                      | 概率 | 应对策略                                                     |
| ------------------ | ------------------------- | ---- | ------------------------------------------------------------ |
| AI 审核服务不可用  | AI 审核与联合审核功能降级 | 中   | 降级为纯规则审核模式，返回明确提示                           |
| PDF 解析格式不统一 | 部分研报内容提取不完整    | 中   | 支持多种解析策略（PyPDF2 + python-docx），失败时返回明确错误 |
| 审核规则覆盖不全   | 部分合规问题漏检          | 低   | 规则 + AI 联合审核互补，持续迭代规则库                       |
| SQLite 性能瓶颈    | 大量并发审核时响应变慢    | 低   | MVP 阶段可接受，后续可迁移至 PostgreSQL                      |

## 8. 立项前置条件（Go / No-Go）

- ☐ 前端页面可独立访问并与后端 API 联调
- ☐ SQLite 数据库文件可正常读写
- ☐ PyPDF2 / python-docx 库可正常解析示例文件
- ☐ 预置审核规则已录入数据库
